# Правила моделі DocTrack

## Реалізована структура

`DocumentRecord` містить дані документа або рахунку. `RecordValidator` перевіряє спільні правила перед збереженням, `RecordDates` задає єдиний формат дат, `statusOn(today)` обчислює статус, а `groupDeadlineRecords(records, today)` формує групи термінів. Ці компоненти не залежать від Android.

`RecordFormInput` містить текстове введення. `validateRecordForm` перетворює дати й суму, викликає `RecordValidator` та повертає помилки для полів або готовий запис. Форма вже реалізована й блокує збереження при помилках.

Список і його зміни зараз зосереджені в `DocTrackApp`. Екрани отримують записи та функції дій через параметри. `recordListSaver` зберігає невеликий навчальний список у saved instance state для відновлення Activity; це не постійне сховище.

## Валідація

| Поле | Правило |
| --- | --- |
| Назва | Після обрізання пробілів — 1–120 символів; правило перевіряє `RecordValidator` |
| Дата видачі | Необов’язкова; рік 1–9999; якщо задана, не пізніше терміну |
| Термін | Обов’язковий `LocalDate`, рік 1–9999; минулі дати дозволені |
| Введення дати | Строго `дд.мм.рррр`, дійсна календарна дата; `01.01.0000` відхиляється |
| Сума рахунку | Обов’язковий `Long > 0` у найменших одиницях валюти |
| Введення суми | Крапка або кома, максимум два десяткові знаки; точне перетворення без округлення та переповнення `Long` |
| Валюта рахунку | EUR, UAH або USD; початково у формі EUR |
| Сума/валюта документа | Відсутні (`null`) |
| Оплата документа | `false`; стан оплати застосовується лише до рахунку |

Дата видачі може збігатися з кінцевою датою або бути в майбутньому. Усі підтримувані валюти мають дві десяткові позиції. Для введення й відображення використовується `RecordDates.formatter` з шаблоном `dd.MM.uuuu`; обмеження років також перевіряється в моделі, тому його не можна обійти майбутнім імпортом.

Валідатор повертає список помилок і не змінює запис. Конструктор `DocumentRecord` сам не запускає валідацію. Майбутні імпорт і серверне API також повинні перевіряти записи перед збереженням.

Редагування зберігає ID, `imagePath` та `recognizedText`. При зміні рахунку на документ форма очищує фінансові поля під час збереження.

## Статуси та поточна дата

| Умова (перевіряється зверху вниз) | Статус |
| --- | --- |
| Рахунок оплачено | `PAID` — оплачено |
| Термін раніше сьогодні, документ | `EXPIRED` — строк дії минув |
| Термін раніше сьогодні, неоплачений рахунок | `OVERDUE` — оплату прострочено |
| Термін сьогодні | `DUE_TODAY` — термін сьогодні |
| Залишилося 1–7 календарних днів включно | `DUE_SOON` — термін наближається |
| Залишилося понад 7 днів | `ACTIVE` — термін ще не наближається |

Вікно 7 днів — прийняте правило першої версії, не окрема вимога викладача. Термін включає весь останній день. Статус обчислюється для перевіреного запису й не зберігається в моделі.

`DocTrackApp` отримує спільну локальну дату через `rememberCurrentDate` та передає її списку, деталям і термінам. Дата перевіряється щохвилини, поки Activity у стані STARTED, та при кожному ON_RESUME. Після повернення з фону вона оновлюється без очікування хвилинного таймера. У фоні таймер зупиняється. Підпис і колір статусу відображає спільний `RecordStatusText`.

Терміни згруповано як минулі, сьогодні, наступні 7 днів і пізніше. Оплачені рахунки приховані з усіх груп, але доступні у «Записах». Порожні групи не показуються; записи відсортовано за датою, назвою й ID.

## Межі поточного етапу та наступна архітектура

Реалізовано: Compose-екрани, навігацію, додавання й редагування у списку в пам’яті, перевірку введення, статуси, групування та відновлення малого навчального стану.

Заплановано: ViewModel, Repository, Room, вибір зображення, OCR, нагадування та серверне API. На діаграмах поточної реалізації їх не можна позначати як готові компоненти. Перед OCR і збільшенням обсягу даних список та великі тексти потрібно перенести в Room; у saved instance state залишити невеликі параметри екрана.
