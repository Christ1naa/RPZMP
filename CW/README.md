# DocTrack

Курсова робота з розробки програмного забезпечення мобільних пристроїв. Android-застосунок для обліку документів, рахунків і термінів із запланованою функцією OCR.

Пакет: `ua.kpi.doctrack`. Інтерфейс: Kotlin, Jetpack Compose, Material 3.

## Поточний стан

- Навігація між вкладками «Записи», «Терміни» та «Сервер» із векторними іконками документа, календаря й сервера.
- Початкові демонстраційні записи та обчислені статуси на картках.
- Перегляд деталей запису, зокрема дати видачі й примітки.
- Вкладка «Терміни»: минулі терміни, сьогодні, наступні 7 днів і пізніше; оплачений рахунок виключено з усіх груп. Картка відкриває деталі.
- Спільна форма додавання та редагування з помилками біля полів.
- Поля рахунку: точна сума в найменших одиницях, валюта EUR/UAH/USD та оплата.
- Збереження змін у списку в пам’яті, повернення до оновлених деталей.
- Підтвердження виходу з незбереженої форми; відновлення введення й демонстраційного списку при відтворенні Activity.
- Модель `DocumentRecord`, перевірка через `RecordValidator` і обчислення статусу через `statusOn(today)`.
- 60 предметних JVM-тестів валідації, дат, статусів, введення та групування термінів.

[Правила моделей, таблиця статусів і приклад використання](docs/model-rules.md).

Форма використовує `RecordValidator`. Дати вводяться строго як `дд.мм.рррр`, минулі дати дозволені. Назва після обрізання пробілів — 1–120 символів; це правило перевіряє валідатор моделі. Роки дат обмежено діапазоном 1–9999, формат введення й відображення спільний. Сума приймає крапку або кому, максимум два десяткові знаки, без округлення й переповнення `Long`. При зміні рахунку на документ фінансові поля очищуються під час збереження; ID та метадані OCR/зображення під час редагування зберігаються.

Постійного сховища, OCR, нагадувань і серверного API ще немає. `recordListSaver` підтримує лише невеликий навчальний список через saved instance state; це тимчасове рішення до Room, а не сховище для великих даних. Після повного закриття й нового запуску зміни можуть бути втрачені. [Сценарії ручної перевірки форми](docs/form-checks.md).

## Перевірки

З папки `CW` у PowerShell:

```powershell
.\gradlew.bat :app:testDebugUnitTest --console=plain
```

2 листопада 2026 року всі 31 новий тест пройшли в окремому JVM-запуску JUnit 4.13.2 (Kotlin 1.9.24, JDK 17, target JVM 11) на незмінених Kotlin-файлах моделі та тестів. Повний Gradle-запуск у середовищі перевірки не відбувся: завантаження дистрибутива Gradle 9.6.0 завершилося помилкою мережі. Збірку Android і запуск на емуляторі для цих змін тут не перевірено.


3 листопада 2026 року 44 тести моделі, статусів і введення форми пройшли в окремому JVM-запуску JUnit 4.13.2 (Kotlin 1.9.24, JDK 17, target JVM 11). Це перевірка чистої Kotlin-логіки; нові Compose-екрани, saved state, збірка Android та емулятор у цьому середовищі не перевірені через відсутність Android SDK. Перед merge потрібно виконати локальну збірку та сценарії ручної перевірки.

Вкладка «Терміни» використовує `groupDeadlineRecords(records, today)` і наявний `statusOn(today)`. Порожні групи приховані; записи відсортовано за датою, назвою та ID. Список, деталі й терміни отримують спільну дату з оновленням щохвилини у стані STARTED та при ON_RESUME; фоновий таймер зупиняється. Оплачені рахунки доступні у «Записах». [Ручні перевірки термінів](docs/deadline-checks.md).

Після додавання групування 3 листопада 2026 року всі 51 JVM-тест моделі, статусів, введення та групування пройшли (JUnit 4.13.2, Kotlin 1.9.24, JDK 17, JVM target 11). XML ресурсів і посилання на рядки перевірено. Збірку Android і поведінку нової вкладки на емуляторі тут не перевірено через відсутність Android SDK.

[Перевірка оформлення та перелік скриншотів для звіту](docs/ui-checks.md). Іконки використовують кольори Material 3 для вибраного й невибраного стану; підписи вкладок залишено. Візуальний перегляд нових іконок на емуляторі, темну тему та адаптацію потрібно перевірити локально.

Після виправлень за перевіркою коду додано єдині `RecordDates`, `rememberCurrentDate` та `RecordStatusText`; типи й валюти у формі переносяться на наступний рядок, а оплата має одну доступну дію для всього рядка. Додано пряму залежність `lifecycle-runtime-compose` тієї самої версії, що й наявний `lifecycle-runtime-ktx`. Поточну та заплановану архітектуру розділено в `docs/model-rules.md`. Android-збірка, Lint, lifecycle та TalkBack потребують локальної перевірки.

3 листопада 2026 року після виправлень рев’ю всі 60 предметних тестів пройшли в окремому JVM-запуску JUnit 4.13.2 (Kotlin 1.9.24, JDK 17, target JVM 11). Додані 9 перевірок охоплюють межі довжини назви в моделі, діапазон років, рік 0000, високосні дати та незмінність року при перетворенні форми. XML рядків і каталог версій перевірено. Android-збірку, Lint та перевірку UI тут не виконано.
