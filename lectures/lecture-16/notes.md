# Лекція 16 — Основи корутин, coroutineScope, launch та Job

## Основне

### Навіщо потрібні корутини

- **Корутина** — обчислення, виконання якого може призупинитися й пізніше продовжитися. Це дозволяє описати очікування послідовним кодом і координувати кілька завдань.
- **Конкурентність** означає, що кілька завдань просуваються протягом спільного проміжку часу. **Паралельність** — фактичне одночасне виконання на різних потоках/ядрах. Launch сам по собі не гарантує паралельність.
- Корутина не є окремим потоком ОС. Один потік може виконувати різні корутини, поки інші очікують. Залежно від диспетчера корутина може продовжитися на іншому потоці.
- `suspend` є частиною мови, а launch, delay, Job та більшість засобів керування надає зовнішня бібліотека `kotlinx.coroutines`.

### Suspend-функції та очікування

```kotlin
suspend fun doWork() {
    delay(100L)
    println("Готово")
}
```

- Suspend дозволяє функції мати точки призупинення; не означає, що вона обов'язково призупиниться, почне виконуватися у фоні чи створить нову корутину.
- Прямий виклик `doWork(); println("Далі")` чекає повернення doWork. Усередині поточної корутини порядок лишається послідовним.
- Suspend-функцію викликають із suspend-контексту: іншої suspend-функції або відповідного блоку корутини.
- `delay(100L)` призупиняє корутину, не займаючи потік очікуванням. `Thread.sleep(100L)` блокує потік. Заміна назви функції на suspend не зробить блокувальний код неблокувальним.
- Delay приймає час у мілісекундах; короткі затримки тут лише імітують роботу. Реальні мережеві запити потребують відповідного API.

### Scope, context і життєвий цикл

- **CoroutineScope** визначає область запуску та керування дочірніми корутинами.
- **CoroutineContext** — набір елементів, наприклад Job і диспетчер. Область і контекст пов'язані, але це не одне поняття.
- `coroutineScope { ... }` — suspend-функція, яка створює вкладену область й повертається після завершення її блоку та всіх дочірніх корутин.
- Її очікування призупиняє поточну корутину, а не блокує потік.
- `launch { ... }` усередині області створює дочірню корутину, дозволяючи батьківському коду продовжитися.
- **Структурована конкурентність** пов'язує життєві цикли: батько чекає дітей; скасування батька поширюється на них. Звичайний збій дитини у coroutineScope скасовує пов'язану роботу й передається назовні.

```kotlin
suspend fun loadDemo() = coroutineScope {
    launch { doWork() }
    println("Дочірня робота запущена")
}
// Після повернення з loadDemo дочірня корутина вже завершена.
```

Вкладений launch за замовчуванням належить поточній області. Завершення **тіла** зовнішньої корутини ще не означає завершення її Job, якщо дитина досі працює.

### Launch і Job

| Засіб | Призначення |
| --- | --- |
| `launch { ... }` | Виконати роботу без повернення її значення виклику |
| `Job` | Стежити за станом і керувати життєвим циклом |
| `job.join()` | Призупинити поточну корутину до завершення job |
| `job.start()` | Запустити відкладену корутину |
| `job.cancel()` | Запросити скасування; докладніше в лекції 17 |
| `isActive` | Job зараз активний |
| `isCompleted` | Job остаточно завершений, включно зі скасуванням |
| `isCancelled` | Job скасований, зокрема через збій |

- Join не повертає обчислений результат. Для результату призначений async/await із лекції 17.
- Scope і без явного join чекає дітей перед поверненням. Join потрібен, якщо **конкретний наступний крок** має чекати конкретну роботу.
- Join не є способом перехопити виняток дитини; у звичайній ієрархії збій може скасувати батька.

### Відкладений запуск

```kotlin
val job = launch(start = CoroutineStart.LAZY) { doWork() }
job.start()
job.join()
```

- LAZY створює Job без запуску тіла. Start запускає його; join також може запустити lazy Job й одразу дочекатися завершення.
- Початковий lazy Job має isActive=false, isCompleted=false. Це не те саме, що вже завершена корутина.
- Незатребувану lazy-дитину потрібно скасувати: її батько може залишитися чекати незавершену роботу. Не залишайте LAZY без start/join або cancel.
- Без LAZY запуск запитується одразу, але точний момент виконання тіла залежить від контексту та планувальника.

### Точка входу прикладів

У `tasks.kt` використано `fun main() = runBlocking { ... }`. RunBlocking створює міст від звичайного консольного main до корутин і **блокує потік виклику** до завершення своєї роботи. Його успадкований диспетчер у цих прикладах виконує дітей у потоці main.

У PDF є інший коректний запис: `suspend fun main() = coroutineScope { ... }`. RunBlocking обрано для послідовного консольного запуску всіх прикладів. **Не переносіть runBlocking на головний потік Android UI.** Там використовують області відповідного життєвого циклу, наприклад viewModelScope.

## Приклади з `tasks.kt`

Це **навчальні приклади за змістом PDF**, а не окремо сформульовані викладачем практичні завдання. Окремого переліку завдань чи контрольних запитань у PDF немає.

1. Послідовний виклик suspend-функції: наступний рядок чекає її повернення.
2. Launch у coroutineScope: батьківський блок продовжується, але вся область чекає дитину.
3. Дві конкурентні роботи A/B; взаємний порядок їхнього виведення не фіксується.
4. Вкладена корутина та очікування outer.join() разом із її завершенням.
5. Окремий Job і явна межа «перед join / після join».
6. LAZY: start, автоматичний запуск через join, скасування невикористаної дитини.
7. Назва потоку до/після delay у контексті runBlocking: конкурентність можлива в одному потоці.

## Питання для самоперевірки

Навчальні питання з короткими відповідями, додані для повторення.

1. Чи suspend запускає функцію у фоні? Ні, лише дозволяє призупинення.
2. Що відбувається з потоком під час delay? Він може виконувати іншу роботу.
3. Чи launch обов'язково створює потік? Ні.
4. Коли coroutineScope повертається? Коли завершені блок і його діти.
5. Навіщо join, якщо scope вже чекає дітей? Щоб конкретна інструкція всередині scope виконалася після певної дитини.
6. Чи завершений Job із isActive=false? Не обов'язково: це може бути ще не запущений lazy Job.
7. Чи join може запустити LAZY? Так.
8. Чому runBlocking не підходить для Android UI? Блокує головний потік.

PowerShell:

```powershell
New-Item -ItemType Directory -Force "C:\Tools\kotlin-libs" | Out-Null
Invoke-WebRequest -Uri "https://repo.maven.apache.org/maven2/org/jetbrains/kotlinx/kotlinx-coroutines-core-jvm/1.10.2/kotlinx-coroutines-core-jvm-1.10.2.jar" -OutFile "C:\Tools\kotlin-libs\kotlinx-coroutines-core-jvm-1.10.2.jar"
```

Якщо файл уже завантажено для лекції 16, повторювати завантаження для 17–18 не потрібно. JAR зберігається поза репозиторієм.

### 2. Скомпілюйте й запустіть поточну лекцію

CMD:

```cmd
cd C:\Projects\RPZMP\lectures\lecture-16
"C:\Tools\kotlinc\kotlinc\bin\kotlinc.bat" tasks.kt -cp "C:\Tools\kotlin-libs\kotlinx-coroutines-core-jvm-1.10.2.jar" -include-runtime -d tasks.jar
java -cp "tasks.jar;C:\Tools\kotlin-libs\kotlinx-coroutines-core-jvm-1.10.2.jar" TasksKt
```

PowerShell:

```powershell
cd C:\Projects\RPZMP\lectures\lecture-16
& "C:\Tools\kotlinc\kotlinc\bin\kotlinc.bat" tasks.kt -cp "C:\Tools\kotlin-libs\kotlinx-coroutines-core-jvm-1.10.2.jar" -include-runtime -d tasks.jar
java -cp "tasks.jar;C:\Tools\kotlin-libs\kotlinx-coroutines-core-jvm-1.10.2.jar" TasksKt
```

Замініть шлях до kotlinc, якщо він встановлений в іншій папці. Компілюйте лекції **окремо**: кожна має власний main і може повторювати імена класів/функцій.

- `-cp` при компіляції дає компілятору бібліотеку корутин; при запуску вона також має бути в classpath.
- `-include-runtime` додає Kotlin runtime у tasks.jar, але **не пакує** зовнішню бібліотеку корутин усередину.
- Тому тут потрібен `java -cp ... TasksKt`, а не старий `java -jar tasks.jar`. На Windows роздільник classpath — крапка з комою `;`; TasksKt — JVM-клас із main, згенерований із tasks.kt.
- Якщо бачите `unresolved reference: kotlinx`, перевірте завантажений JAR і параметр -cp. Якщо `NoClassDefFoundError: kotlinx/coroutines/...` — перевірте classpath саме команди java.
- Не додавайте згенерований tasks.jar у Git. Після редагування збережіть tasks.kt і повторіть компіляцію.

## Що запам'ятати та уточнення до PDF

- Версія kotlinx.coroutines 1.5.2 у PDF — старий приклад. Тут закріплено 1.10.2 для відтворюваності; це не твердження про найновішу версію.
- Launch запускає конкурентне завдання; слово «паралельно» в PDF не гарантує іншого потоку чи ядра.
- CoroutineScope не завжди встановлює Dispatchers.Default: контекст зазвичай успадковується. Контекст runBlocking у наших прикладах відрізняється від контексту suspend main у PDF.
- Join призупиняє очікувача, а не блокує його потік. RunBlocking — інший механізм, який саме блокує.
- На с. 12 `Val` потрібно писати `val`. На рисунку 8.9 пропущено рядок Start із наведеного коду.
- Не очікуйте єдиного взаємного порядку виведення незалежних корутин; важливі явні залежності й очікування.
