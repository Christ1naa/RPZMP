## Мета й прийняті рішення

Розробити окремий Android-застосунок прогнозування споживання для вигаданих споживачів. Відповідно до с. 45 методички використано основу Empty Compose Activity. Попередні роботи показують перехід від UI до MVVM/Room і REST; у PW04 використано ці архітектурні навички, але джерела локальні, як дозволено на с. 48. Зовнішній сервіс потрібен лише для справжніх картографічних тайлів.

## Архітектура

`DemoSites → DemoTelemetrySource → TelemetryEngine → ForecastViewModel → Compose`.

`SiteQuery → querySites → visible → LazyColumn + GoogleMap`.

`LocationManager → callbackFlow → STARTED lifecycle → маркер користувача`.

Моделі не залежать від UI. У логіці немає Android API. ViewModel має ін'єкцію engine/failureAction для тестів. UI передає дії та відображає StateFlow через collectAsStateWithLifecycle. `ui/SiteDetails.kt` має окремий маршрут `details/{id}` і знаходить об'єкт за стабільним ID у повному наборі, незалежно від фільтра. ID кодується як сегмент шляху; повторний перехід використовує launchSingleTop. Завантаження, недоступне джерело та невідомий ID після успішного завантаження мають різні повідомлення; є повернення й відновлення після збою.

## Асинхронна обробка

Холодний потік лічильника генерує кадр щосекунди. Прогнозний коефіцієнт генерується окремо раз на 1,5 с. `filter` перевіряє повноту кадру, невід'ємність і скінченність; `map` перетворює Вт на кВт. `combine` реагує на кожне нове значення будь-якого джерела.

Обидва джерела мають незалежні watchdog та бюджети повторів. Від початку спроби й після кожного валідного значення дозволено 5 с до наступного; відкинуті filter значення не скидають таймер. Чисте завершення потоку також означає відсутність даних, оскільки контракт джерела безперервний. Для NO_DATA та IOException є максимум три повтори із затримками 1, 2, 3 с на джерело за одну сесію; один добрий кадр не обнуляє бюджет. Скасування не повторюється, не-IO помилки завершують відповідне джерело FAILED.

Під час збою `runningFold` зберігає останній повний узгоджений прогноз і позначає його застарілим. Новий коефіцієнт не змінює прогноз на основі старого кадру; здорове джерело продовжує працювати. Після відновлення обох LIVE використовується їхня остання валідна пара. UI показує окремі статуси лічильника/моделі, причину, номер повтору та застарілість. До першого узгодженого результату показано «Немає даних», а не виміряний нуль.

«Збій лічильника» та «Збій моделі» одноразово спричиняють IOException у відповідному наступному вимірі. «Відновити» через flatMapLatest скасовує обидва старі джерела та створює нову сесію з чистими бюджетами. Реалізація й virtual-time перевірки докладно описані у stage-2-flow.md.

`shareIn(viewModelScope, WhileSubscribed(5000, 0), replay=1)` створює спільний гарячий потік, який продукує значення незалежно від окремих UI-колекторів протягом активної сесії. Після останньої відписки генератори зупиняються через 5 с; replay очищається. Похідний uiState теж очищає replay при відписці, щоб після зупинки не показувати старий LIVE до нових даних. Постійної фонової роботи після закриття застосунку немає.

## Список, фільтри й мапа

Фільтри застосовуються одночасно: назва, тип, статус, включні межі встановленої потужності. Десяткові числа підтримують кому/крапку й експоненційний запис; NaN, нескінченність, від'ємні, шістнадцяткові, суфікси f/d, переповнення та ненульові значення, які перетворюються на нуль Double, відхиляються. Порожня межа не обмежує діапазон; мінімум більше максимуму дає окрему помилку. Незмінний SiteQuery розбирає межі один раз, а не для кожного об'єкта.

Сортування має перший, другий критерій і стабільний ID. Український Collator із SECONDARY та CANONICAL_DECOMPOSITION не змінює порядок через регістр або канонічний запис літери; для пошуку назва й обрізаний запит нормалізуються в NFC. Потужність/прогноз порівнюються як числа, дата опису — як Instant, тип/статус — за українськими підписами. Спадання змінює обидва критерії; ID за повної рівності лишається за зростанням. Однаковий перший/другий критерій допустимий, друге порівняння тоді надлишкове. Зміни панелі застосовуються одразу; «Готово» закриває її, обидві дії скидання очищають усі поля. Підсумок над списком показує кількість, порядок критеріїв і напрямок. Деталі перевірки — у stage-4-query.md.

Натискання картки обирає об'єкт і відкриває окремий екран деталей за ID, як вимагає с. 25. Кнопка «На мапі» обирає об'єкт без навігації; «Деталі» дублює явний перехід. Кожна явна дія має selectionRevision, тому повторний вибір того самого ID теж запускає фокус і прокрутку; нові виміри та сортування не створюють цієї події. A04 підтверджено на справжньому SDK фізичного SM-A546B: повторний ID після pan повертає камеру, нові дані самі її не рухають. MarkerInfoWindow відкриває власний SiteInfoWindow через false у callback, обирає ID й прокручує LazyColumn. Стандартний snippet на телефоні обрізав опис; власний вміст переносить усі поля, а адаптивний верхній contentPadding лишає місце над центром камери в короткому слоті. Відфільтрований об'єкт не залишає активного виділення. Реалізація та історія перевірок мапи — у stage-5-map.md.

Етап 3 явно підписує встановлену потужність, виміряне навантаження та добовий прогноз; картки й деталі розрізняють дату опису та час виміру. Порожній початковий набір відрізняється від нуля збігів пошуку. Службові повідомлення й картки прокручуються в одному LazyColumn зі стабільними ключами. У широкому/альбомному вікні список і мапа стоять поруч; у портретному мапа обмежена часткою висоти. Перемикач видимості мапи зберігається через rememberSaveable. Вміст деталей розбитий на окремі lazy-елементи, а «Назад» залишається поза прокручуваним вмістом. Перевірки та межі — у stage-3-catalog.md.

## Геолокація

Обрано системний LocationManager, прямо дозволений домашнім завданням. Точний дозвіл використовує GPS і доступне мережеве джерело; приблизний — мережеве. Місцезнаходження не вигадується й застаріле lastKnown не видається за поточне. Запити обмежено 5 с/10 м. callbackFlow видаляє слухача через awaitClose; lifecycle STARTED обмежує роботу видимим екраном.

Відсутність дозволу, провайдера, вимкнена геолокація та SecurityException відображаються користувачу. Повернення з налаштувань повторно запускає перевірку дозволів і збір. Кнопка «Моя позиція» запитує доступ і фокусує мапу після свіжого виміру. Зелений маркер користувача відокремлений від червоних/блакитного маркерів споживачів.

## Адаптивність і збереження стану

Заголовок каталогу відокремлено від дій; FlowRow переносить кнопки. Підсумок запиту має максимум два рядки, повні критерії доступні в панелі фільтрів. Панель одразу розгортається на доступну висоту (skipPartiallyExpanded=true); «Скинути» та «Готово» — окремі елементи LazyColumn. Це виправляє підтверджене тестом обрізання дій при fontScale=2. Fallback без мапи прокручується навіть у слоті 320×180 dp.

На Pixel_6 / API 36 фактично перевірено MainActivity у CREATED/RESUMED та зміни Configuration landscape → portrait: запит «Офіс», вибір office-1 і прихована мапа збереглися. Синтетичний viewport 320×480 dp з fontScale=2 підтвердив доступність останньої картки, деталей і дій фільтрів. Ці тести не є process death, TalkBack або ручним оглядом усіх пристроїв.

## Висновки та обмеження

Побудовано окремий застосунок варіанта №1 із двома асинхронними джерелами, перетвореннями Flow, спільним станом, незалежним відновленням джерел, картками/деталями, одночасними фільтрами й двома критеріями сортування. Координати користувача отримуються через foreground LocationManager; програмно інтегровані маркери та двосторонні дії мапи.

Модель прогнозу демонстраційна: шість вигаданих споживачів, локальні дані, без навчання на історії чи доведеної точності для реального електроспоживання. Описаний алгоритм є самостійним рішенням для варіанта, а не заданим викладачем методом прогнозування. Виміри не зберігаються між процесами, фонової служби немає.

Реалізація й перевірки просунутого рівня завершені в описаних межах: 54 JVM і 64 унікальні Android-методи пройшли в кількох конфігураціях. Справжня Maps, InfoWindow, камера, системні дозволи, негативні мережеві сценарії та немокований network provider підтверджено. Для зеленого маркера й руху використано позначені test providers Києва, без збереження приватної фізичної позиції. Супутниковий GNSS, process death від ОС, TalkBack і foldable не перевірялися. Оформлені DOCX і PDF вже підготовлено та наведено на початку цього документа. Подання й захист залишаються окремими діями. Матриця — [requirements.md](requirements.md), 48 відповідей — [control-questions.md](control-questions.md).

Оригінальні GoogleMap.snapshot з фізичного телефону й підписи — [evidence/maps-phone](evidence/maps-phone/README.md). Для цільового Maps/UI-набору AndroidJUnitRunner повідомив OK (4 tests). Попередній Gradle connected task повернув failure попри 2/2 успішних JUnit/XML; аномалію не приховано, точна причина не встановлена. Повторний прямий runner підтвердив результат.
