# Етап 4 — пошук, фільтри та сортування

Робоча гілка `feature/pw04`, база `032c588`; локальні зміни етапів 1–3 збережено. Обсяг — вимоги занять №15 (с. 31, 36–37) та фільтрація/сортування списку з №14 (с. 26), спільні для мапи параметри з №16 (с. 48–49). Перевірка справжніх маркерів і Google Maps SDK залишається етапом 5.

## Визначена поведінка

| Частина | Контракт |
|---|---|
| Пошук | Підрядок у назві без урахування регістру; зовнішні пробіли прибираються; запит і назва нормалізуються NFC. Порожній запит дозволяє всі назви. Нечіткий пошук/пошук за описом не заявляються |
| Умови | Назва AND тип AND статус AND мінімум AND максимум; пропущена умова не обмежує набір |
| Потужність | Встановлена потужність `ratedPowerKw`, а не виміряне навантаження або прогноз |
| Межі | Включні; можна задати одну, обидві або жодної. Нуль — допустима межа, порожнє поле — відсутня межа |
| Формат | Десятковий запис із комою/крапкою, необов'язковим плюсом і експонентою: `12,5`, `.5`, `+12`, `1,2e2`; зовнішні пробіли дозволені |
| Невалідні значення | Від'ємний знак (у тому числі `-0`), NaN/Infinity, hex, суфікси f/d, групування розрядів, змішані розділювачі, одиниці в полі, неповна експонента, overflow; nonzero underflow у нуль Double теж відхиляється |
| Помилка меж | Повідомлення про мінімум/максимум або «Мінімум перевищує максимум»; visible порожній, але UI не називає це нулем збігів пошуку |
| Сортування | Перший критерій → другий критерій → ID; усі 6 критеріїв доступні в обох полях |
| Критерії | Назва, тип, встановлена потужність, дата опису `updatedAt`, статус, добовий прогноз `forecastDailyKwh` |
| Текст | Український Collator SECONDARY з canonical decomposition; регістр не міняє порядок, літери Ґ/Є/І/Ї зберігають власні позиції |
| Числа/дати | Потужність та прогноз — Double; дата — Instant, а не рядок форматованої дати або `sampledAt` |
| Напрямок | Один перемикач змінює обидва вибрані критерії; це явно підписано. Остаточний ID лишається за зростанням і не залежить від вхідного порядку |
| Повторені критерії | Допустимі: другий не змінює результат першого; за рівності спрацьовує ID |
| Застосування | Одразу при зміні поля; «Готово» закриває панель, не є відкладеним apply |
| Скидання | «Скинути» у панелі та «Скинути фільтри» у списку повертають весь SiteQuery до початкового: пошук, тип, стан, межі, обидва критерії, напрямок |

BigDecimal використано тільки для розбору десяткового введення й виявлення переповнення/втрати ненульового значення в нуль; основні моделі й порівняння лишаються Double. Це не обіцянка довільної десяткової точності розрахунку. Звичайне округлення скінченних значень Double прийнятне для навчальної моделі. Незмінний SiteQuery розбирає межі один раз під час створення, а не в кожному проході filter.

## UI і збереження

У панелі є пояснення одночасної дії умов, явна назва встановленої потужності, десяткова клавіатура, Next/Done та облік IME-відступу. Помилка відображається у панелі й над результатом. Підсумок показує «знайдено з усього», перший/другий критерій і напрямок. Перемикач спадання доступний по всьому рядку, включно з підписом.

SavedStateHandle зберігає всі сирі значення полів та enum-імена, а похідні parsed/normalized значення відновлюються через SiteQuery. Сортування не скидає видимий selectedId; новий прогноз може перемістити вибраний об'єкт, але ID не змінюється. Якщо фільтр/помилка приховує об'єкт, вибір очищається й не з'являється знову автоматично після скидання. Повний початковий набір не змінюється.

Каталог і мапа отримують одну visible-колекцію. UI-тести використовують тестовий слот, який показує її ID; це підтверджує передачу результату через слот, але не рендер/координати справжнього Google Maps SDK.

## Покриття перевірками

- `SiteQueryAdvancedTest`: відомі очікувані ID для 6 перших критеріїв × 2 напрямки; кожен із 6 других критеріїв розв'язує рівність першого; повні збіги/регістр/повторений критерій дають стабільний ID; український алфавіт; NFC-пошук; допустимі й недопустимі числа; однобічні/рівні межі.
- У тому самому класі один тест виконує **240 перевірок комбінацій**, а не 240 окремих JUnit-тестів: 4 варіанти типу × 3 статуси × 4 запити × 5 діапазонів. Очікувані набори ID задані вручну для кожної умови; їх перетин перевіряє AND.
- `ForecastViewModelTest`: усі поля відновлюються з копії handle, сортування зберігає видимий вибір, прихований вибір очищається, зміна прогнозу змінює порядок без підміни ID.
- `FilterPanelTest`: повна комбінація «Офіс + Активний + 30,0–50 кВт + пошук» лишає office-1 у списку й тестовому слоті; помилка 50–10 та скидання; усі 6 перших критеріїв у двох напрямках через справжні Dropdown/Checkbox; окреме скидання у відкритій панелі.
- `AppSmokeTest.completeFilterPanelIsWiredToViewModelAndRestoredAfterRecreation`: реальна MainActivity, тип/статус/кома в межах/дата/напрямок → один об'єкт → recreate Activity → усі значення й результат збережені → скидання повертає 6 об'єктів.
- `AndroidCollationTest`: Ґ/Є/І/Ї перевірено окремо у runtime Android, не лише на JVM розробника.

Фактичні запуски, цифри й можливі невдалі спроби — [verification.md](verification.md). Автоматичні результати не називаються ручною перевіркою. Знімків панелі/результату для фінального звіту ще немає; потрібні справжні знімки повної комбінації office-1, помилкового діапазону, скидання та сортування з напрямком.
