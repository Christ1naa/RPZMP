# Етап 2 — Flow, відсутність даних і відновлення

Дата: 11.11.2026. Робоча гілка `feature/pw04`, база `032c588`; збережено локальні зміни завершеного етапу 1. Зміни обмежено PW04, commit/push не виконуються.

## Результат

Закрито A02/A03 з аудиту: обидва незалежні джерела контролюють надходження валідних даних, мають обмежені автоматичні повтори й показують власний стан. За відсутності даних більше немає необмеженого WAITING або прихованого LIVE зі старими значеннями. До першого повного прогнозу немає фіктивного нуля. Під час збою останній повний прогноз заморожено та позначено застарілим. Каталог розрізняє помилку джерела і порожній результат фільтра.

Це реалізація заняття №13: холодні потоки, перетворення, фільтрація, ViewModel, combine, retryWhen/catch, гарячий shareIn та демонстрація відновлення. Автоматичні тести на AVD підтверджують саме описані UI-сценарії; ручних перевірок і знімків екрана цього етапу не заявляємо. Maps/GPS не входять до цього підтвердження.

## Політика джерел

| Параметр | Поведінка |
|---|---|
| Нормальний ритм | Лічильник кожну 1 с; модель кожні 1,5 с |
| Валідний лічильник | Є всі ID колекції; Вт скінченні й невід'ємні; map переводить Вт у кВт; нуль дозволено |
| Валідна модель | Скінченний коефіцієнт 0–2; demo генерує 1,00–1,10 |
| Вікно даних | 5 с від старту кожної спроби до першого валідного значення та від кожного валідного до наступного |
| Невалідні значення | Відкидаються до watchdog і не скидають його таймер |
| Empty/нормальне завершення | NO_DATA негайно: джерела за контрактом безперервні |
| Мовчання | NO_DATA після 5 с; попередній producer скасовується перед повтором |
| Що повторюється | IOException і NO_DATA, окремо для кожного джерела |
| Бюджет | 3 повтори, тобто не більше 4 підписок на джерело за одну сесію |
| Backoff | 1, 2, 3 с; таймер нового вікна запускається після відповідної затримки |
| Чи обнуляє бюджет один добрий кадр | Ні; це унеможливлює нескінченний цикл «один кадр — збій» |
| Інші помилки | SOURCE_ERROR, FAILED без автоматичного повтору |
| Скасування | CancellationException поширюється, не перетворюється на FAILED/retry |
| Ручне «Відновити» | flatMapLatest скасовує всю стару сесію, створює нові джерела, бюджети починаються з нуля |

Поріг 5 с є рішенням реалізації, а не числом із методички: він перевищує нормальні періоди 1/1,5 с й дає короткий, передбачуваний час реакції. Для повністю мовчазного джерела FAILED настає не пізніше ніж через 4×5 + 1+2+3 = 26 с активного збирання; для негайного IOException/empty — через 6 с. Здорове джерело при цьому не перезапускається.

Watchdog вимірює інтервал надходження валідних значень корутинним таймером, а не різницю системних timestamp. `sampledAt` залишається часом, переданим лічильником; у demo це Instant.now(). Контракт віддалених джерел та перевірка їхнього серверного часу не заявляються.

## Стан і узгодженість

`SourceStatus` містить phase, retries/maxRetries та тип проблеми без тексту винятку. У UI не потрапляють довільні повідомлення від джерел. У `TelemetryState` зберігаються два статуси й останній узгоджений набір показників.

Загальний пріоритет: FAILED → RETRYING → WAITING → LIVE. LIVE можливий тільки коли обидва джерела мають валідні значення та обидва LIVE. `combine` оновлюється від будь-якого джерела; `runningFold` перераховує прогноз лише для такої LIVE-пари. За будь-якого іншого стану набір readings і factor залишається попереднім; `isStale` істинний, якщо вже є readings. Період очікування першого результату не називається застарілим, бо результату ще немає.

Обидва статуси видимі навіть при одночасних різних збоях. До завершення watchdog останнє отримане значення вважається свіжим у межах установленого вікна; після спливу вікна автоматично позначається застарілим. Після відновлення використовується актуальна пара останніх валідних значень.

## Гарячий потік і життєвий цикл

`shareIn(viewModelScope, WhileSubscribed(5000, 0), replay=1)` створює один спільний producer для UI. Кілька колекторів не множать лічильники. Після останньої відписки джерела зупиняються через 5 с; після зупинки очищається replay. Це не постійна фонова служба.

Похідний uiState використовує `WhileSubscribed(0, 0)`, тому старий LIVE не відтворюється після зупинки джерел перед новим кадром. Фільтри й ID зберігаються окремо у SavedStateHandle/StateFlow. Підписка після повної зупинки створює нові джерела та проходить WAITING → LIVE. Скасування scope, перезапуск і закриття downstream скасовують child producer, канал і таймер. Таймаут не є зовнішнім CancellationException: лише власне вичерпання часу перетворюється на NO_DATA.

## UI та демонстрація

- Моніторинг: окремі рядки «Лічильник» і «Модель», причина, лічильник повторів, загальний стан, «Останні дані застарілі».
- До першого повного результату: «Немає даних» і тире для навантаження/коефіцієнта; справжнє нульове споживання лишається допустимим.
- Каталог: StreamStatus у прокручуваному списку, кнопка «Відновити» після FAILED; NO_DATA не підміняється порожнім пошуком. Позиція прокрутки до вибраного ID враховує цей службовий елемент.
- Деталі: застарілі дані супроводжуються тим самим станом джерел.
- «Збій лічильника» і «Збій моделі»: одноразовий IOException у наступній емісії відповідного demo-джерела. Вони дозволяють показати RETRYING → LIVE незалежно.

Демонстраційний сценарій: дочекатися двох LIVE → «Збій лічильника» → RETRYING та позначка застарілості → автоматичний LIVE → «Збій моделі» → аналогічне відновлення. Тест `bothDemoSourcesShowFailureAndRecoverInRealActivity` виконує цей сценарій у справжній MainActivity на AVD. Додаткові virtual-time тести доводять математичні затримки, freeze прогнозу та очищення producer; UI-тест сам по собі не вимірює backoff з точністю до мілісекунди.
