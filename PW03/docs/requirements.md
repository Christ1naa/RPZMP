## 1. Призначення

Застосунок прогнозує споживання електроенергії за параметрами
приладів і дозволяє використовувати енергетичні сценарії,
отримані через навчальний REST API.

Приклад сценарію — «Домашній офіс» зі списком приладів,
їх потужністю, кількістю та часом роботи.

- Navigation Compose;

## 4. Правила предметної області

Добове споживання приладу:

E_day = powerWatts / 1000 × hoursPerDay × deviceCount

Добове споживання сценарію — сума споживання його приладів.

Прогноз за період:

E_period = E_day × forecastDays

Одиниця результату — кВт·год.
Період — від 1 до 365 днів.

Для приладів із API застосовуються ті самі числові межі,
що й у наявному DeviceValidator.
Ідентифікатори та назви не можуть бути порожніми.
Числа мають бути скінченними.

Сценарій містить від 1 до 50 позицій.
Ідентифікатори сценаріїв у списку та приладів у межах
одного сценарію мають бути унікальними.

Імпорт додає прилади до поточного профілю з новими локальними ID.
Наявні прилади та встановлений період зберігаються.
Якщо загальний ліміт 50 позицій буде перевищено,
імпорт відхиляється повністю.

## 5. Правила кешу

- Room зберігає останню коректно завантажену версію сценаріїв.
- При відкритті екрана спочатку показується наявний кеш.
- За наявності мережі виконується оновлення з API.
- Користувач може запустити оновлення вручну.
- Успішне оновлення списку атомарно замінює кеш сценаріїв.
- Пошкоджений JSON або невалідні дані не змінюють кеш.
- Невдала спроба оновлення залишає попередні дані
  з повідомленням, що оновлення не виконано.
- UI показує час останнього успішного оновлення
  та ознаку відображення кешованих даних.
- Відсутність кешу без мережі показується як порожній стан
  із поясненням, а не як успішне завантаження.

Каталог сценаріїв спільний для навчальних користувачів.
Персональні прилади та історія залишаються розділеними
за користувачами.

## 6. Правила сесії та ролей

USER:
- перегляд сценаріїв;
- локальний прогноз та імпорт;
- власні прилади та історія.

ADMIN:
- усі можливості USER;
- перегляд адміністративного підсумку API.

Роль надходить у токені, а не визначається за текстом email.

Після запуску застосунок спочатку читає збережену сесію.
Поки читання не завершено, захищений UI не показується.

Без мережі дозволений перегляд локальних даних
за наявності непростроченої збереженої сесії.
Новий вхід потребує зв’язку із сервером.

При виході або завершенні сесії захищений UI закривається.
Персональні дані в Room не видаляються і не передаються
наступному користувачу.

Локальна перевірка строку дії потрібна для UI.
Достовірність токена та право доступу перевіряє сервер.

## 7. Межі роботи

- Сервер навчальний, працює локально.
- Облікові дані вигадані.
- Реєстрація через API не входить до ПР3.
- Автоматичне оновлення токена не реалізується:
  після завершення сесії потрібен повторний вхід.
- Персональні прилади та історія не синхронізуються із сервером.
- Адміністрування обмежене переглядом підсумку.
- Окремий режим вибору рівня складності не потрібний.

Робота готова, коли вимоги підтверджено реалізацією
та перевірками, застосунок збирається, результати тестів
зафіксовано, а звіт відповідає фактичному стану проєкту.
