## Архітектура та докази

Пакети domain (чисті моделі/формули), data (демоісторія, SensorRepository, налаштування/журнал), notifications (worker/receiver/канали), ui (ViewModel/StateFlow, екрани, charts/components). UI збирає стан через collectAsStateWithLifecycle; сенсорна підписка лише під час видимого екрана, плановані нагадування незалежні від нього. Параметри та журнал зберігати локально; секретів і сервера для локальної частини не потрібно.

Ще зібрати оригінальні кадри: два часові стани реальних сенсорів; відсутній сенсор; вибір/поріг/фільтр/сортування; локальне повідомлення; кілька каналів/повідомлень; підтвердження й відкладання з відповідним UI; відмова дозволу; лінія, стовпчики з підказкою, комбінований графік у двох масштабах/інтервалах; індикатор нахилу, дуга, два вектори та змінений стиль; landscape і великий шрифт. Зараз кадрів PW05 немає.

## Неоднозначності й передумови

С. 145 задає лише назву теми, конкретний сенсор і формулу не визначає: обрано акселерометр/гіроскоп/світло для моніторингу, окрему явно демонстраційну історію енергії та прогноз сталого режиму. Це не фізична модель передбачення енергії за рухом телефона. FCM є в теорії (с. 20, 28–29), але відсутній серед обов'язкових рівнів/домашнього завдання; локальні сповіщення виконуються без Firebase. Віддалена push-демонстрація, якщо її окремо вимагатиме викладач, потребує Firebase-проєкту/сервера/облікових даних і не може оголошуватися перевіреною без них. Спеціального шаблону звіту PW05 немає: використовуємо фінальний стиль PW04 та вимоги користувачки.

Потрібні Android SDK 37, JDK/Gradle згідно wrapper, кеш або мережа для залежностей, пристрій/AVD з сенсорами. WorkManager не гарантує точний час доставки. Фізична перевірка сенсорів, звук, анімація й системні дозволи потребують окремих фактичних запусків.

Зміни дозволено лише в PW05. Не комітити, не пушити. Виключати local.properties, ключі, середовища, caches, build/APK та інші генеровані файли; wrapper JAR є необхідним інструментом відтворення збірки.

Архітектурне рішення етапу 3: AlarmManager замість запланованого WorkManager. Це прямо дозволено методичкою; нова залежність не потрібна. Вибрано неточний setAndAllowWhileIdle без exact-alarm permission. FCM залишається лише теоретичним матеріалом, не обов’язковою локальною реалізацією.

Рішення етапу 4: графіки засобами наявної Compose Canvas, без окремої Chart-залежності. Лінія й стовпчики використовують однакові точки. Зони — навчальна частка тієї самої суми; джерело явно демонстраційне.

Власне рев’ю етапу 2 виконано: callback-історію серіалізовано lock, перевірено закриття потоку й відписку; додано STALE 5 с та перевірку покоління timeout відносно timestamp; UI не малює до 360 рядків одразу. SensorEvent копіюється, дані обмежені й перевірені. Сенсорні фізичні величини залишаються окремими від демонстраційних кВт·год.

Критерії на рівні коду реалізовано для всіх занять, але повний пристроєвий захист не оголошується завершеним: AVD не замінює фізичний телефон. Діапазон 81–100 не є гарантованою оцінкою.

Наступні конкретні дії: фізичний телефон і кадри зміни датчиків; звук/вібрація; reboot, Doze та process-death; додаткові API/шрифт 200%; після доказів — оновити протокол і звіт. Commit/push і подання дозволом цієї задачі не передбачені.



Додатково підтверджено UI окремих графіків, масштаб 2× і категорійну підказку; оригінали 10–13.
